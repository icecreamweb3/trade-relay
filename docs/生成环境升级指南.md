# Trade Relay 生产环境升级指南

本文用于将已在测试数据库验证通过的 Trade Relay 版本升级到生产环境，覆盖代码发布、数据库备份与迁移、历史数据处理、功能验收、上线观察和回滚。

> 文档文件名沿用项目约定的“生成环境”，正文统一使用“生产环境”。

## 1. 发布原则

- 只部署已经在测试环境验证并提交到 Git 的固定版本或标签。
- 不直接复制开发工作区，更不能部署包含未提交修改的目录。
- 不把测试环境的 `.env.production`、用户配置或数据库凭证覆盖到生产环境。
- 数据库迁移前必须停止后台写入并完成可恢复的全量备份。
- 升级期间记录统一使用 UTC 时间。
- 历史遗留数据默认保留；只保证升级后新数据按照新的持仓周期模型写入。

## 2. 升级内容

本次 Positions 功能升级主要包括：

- `positions.id` 作为完整持仓周期 ID。
- `orders.position_id` 关联开仓和平仓订单。
- `position_history.position_id` 支持一个持仓周期对应多次平仓记录。
- `position_history_final.position_id` 按持仓周期聚合最终记录。
- `position_history_final.source_history_id` 保留无法关联持仓周期的历史记录。
- 开仓和平仓订单分别写入 `open_orders_id`、`close_orders_id`。
- Positions 页面展示 Open Time、Close Time、MFE、MAE 等复盘指标。
- Positions 页面支持表格选区、整行/整列选择和 `Ctrl+C`。
- Position 行双击打开对应持仓周期 K 线。
- Analyze 从 Orders 页面迁移到 Positions 页面。
- Binance SDK 初始化和时间同步只使用合约接口，不再主动请求现货接口。

## 4. 检查生产配置

生产环境必须继续使用原有 `.env.production`，重点确认：

```env
TRADE_RELAY_MYSQL_HOST=生产数据库地址
TRADE_RELAY_MYSQL_PORT=3306
TRADE_RELAY_MYSQL_USER=生产数据库用户
TRADE_RELAY_MYSQL_DATABASE=生产数据库名

TRADE_RELAY_JWT_SECRET=保持生产现有值
TRADE_RELAY_ENCRYPTION_KEY=保持生产现有值
```

`TRADE_RELAY_ENCRYPTION_KEY` 不能改变，否则已有 Binance API Key 将无法解密。

逐个确认生产用户：

- Binance API Key 和 Secret 正确。
- API Key 已启用 USD-M 合约权限。
- Binance IP 白名单包含生产服务器公网 IP。
- API Key 没有失效或被删除。
- 网络或代理能够稳定访问 `fapi.binance.com`。

## 9. 执行数据库迁移

虽然后端启动时会自动执行 `init_db()`，生产升级建议在后台停止状态下先单独运行一次：

```bash
.venv/bin/python -c \
"from trade_relay.env_loader import load_env; load_env(); from trade_relay.database import init_db; init_db(); print('DATABASE MIGRATION OK')"
```

迁移会自动处理：

- `orders.position_id`
- `position_history.position_id`
- `position_history_final` 表
- `open_orders_id`
- `close_orders_id`
- 旧 `orders_id` 到 `close_orders_id` 的迁移
- MFE/MAE 指标字段和索引
- 已有关联持仓周期的最终记录聚合

命令必须正常结束并输出：

```text
DATABASE MIGRATION OK
```

如果迁移报错，保持后台停止，不要继续启动生产流量。

## 10. 验证数据库结构

```sql
SHOW COLUMNS FROM orders LIKE 'position_id';
SHOW COLUMNS FROM position_history LIKE 'position_id';

SHOW COLUMNS FROM position_history_final
WHERE Field IN (
    'position_id',
    'source_history_id',
    'open_time',
    'open_orders_id',
    'close_orders_id',
    'metric_status'
);
```

检查最终表两种来源：

```sql
SELECT
    CASE
        WHEN position_id IS NOT NULL AND source_history_id IS NULL
            THEN 'POSITION_CYCLE'
        WHEN position_id IS NULL AND source_history_id IS NOT NULL
            THEN 'LEGACY_HISTORY'
        ELSE 'INVALID'
    END AS source_type,
    COUNT(*) AS record_count
FROM position_history_final
GROUP BY source_type;
```

`INVALID` 应为 0。`LEGACY_HISTORY` 可以保留，它代表无法安全关联 `positions.id` 的旧数据。

## 11. 历史数据处理

### 11.1 默认策略

如果决定不处理历史遗留数据，生产升级时不要运行全量 `--apply`。数据库迁移完成后直接进入后台启动和新数据验收。

### 11.2 可选只读扫描

全量扫描默认是 dry-run，不修改数据库：

```bash
.venv/bin/python task/recalculate_historical_excursion_metrics.py --dry-run
```

按用户扫描：

```bash
.venv/bin/python task/recalculate_historical_excursion_metrics.py \
  --user-id 5 \
  --dry-run
```

按平仓时间扫描：

```bash
.venv/bin/python task/recalculate_historical_excursion_metrics.py \
  --start-time "<CUTOVER_UTC>" \
  --dry-run
```

### 11.3 可选正式修复

确认 dry-run 输出后才能添加 `--apply`：

```bash
.venv/bin/python task/recalculate_historical_excursion_metrics.py \
  --user-id 5 \
  --start-time "<CUTOVER_UTC>" \
  --apply
```

正式修复会访问 Binance 并写生产数据库。执行期间后台必须保持停止，代理和用户 API Key 必须可用。

## 15. 新数据数据库验收

以下 SQL 中的 `<CUTOVER_UTC>` 替换为第 5.1 节记录的实际 UTC 时间。

### 15.1 检查开仓订单关联

```sql
SELECT COUNT(*) AS missing_open_position_links
FROM orders
WHERE filled_at >= '<CUTOVER_UTC>'
  AND status = 'FILLED'
  AND trade_direction = 'OPEN'
  AND position_id IS NULL;
```

预期为 0。

### 15.2 检查平仓历史关联

```sql
SELECT COUNT(*) AS missing_history_position_links
FROM position_history
WHERE created_at >= '<CUTOVER_UTC>'
  AND position_id IS NULL;
```

预期为 0。

### 15.3 检查重复平仓历史

```sql
SELECT position_id, close_order_id, COUNT(*) AS row_count
FROM position_history
WHERE created_at >= '<CUTOVER_UTC>'
  AND position_id IS NOT NULL
  AND close_order_id IS NOT NULL
GROUP BY position_id, close_order_id
HAVING COUNT(*) > 1;
```

预期没有结果。

### 15.4 检查最终表来源

```sql
SELECT COUNT(*) AS invalid_final_rows
FROM position_history_final
WHERE created_at >= '<CUTOVER_UTC>'
  AND (
      (position_id IS NULL AND source_history_id IS NULL)
      OR
      (position_id IS NOT NULL AND source_history_id IS NOT NULL)
  );
```

预期为 0。

### 15.5 检查 MFE/MAE 状态

```sql
SELECT metric_status, COUNT(*) AS record_count
FROM position_history_final
WHERE close_time >= '<CUTOVER_UTC>'
GROUP BY metric_status;
```

完全平仓后短暂显示 `PENDING` 属于正常情况。等待几分钟后，新数据应变为 `CALCULATED`；如果出现 `FAILED`，检查 `positions.excursion_last_error`：

```sql
SELECT id, user_id, username, symbol, position_side,
       excursion_attempts, excursion_last_error
FROM positions
WHERE updated_at >= '<CUTOVER_UTC>'
  AND excursion_status = 'FAILED'
ORDER BY updated_at DESC;
```

## 16. 上线后观察

建议至少观察 30–60 分钟：

- 新开仓成交是否及时生成并关联 `position_id`。
- OPEN 和 CLOSE 订单是否都关联同一个持仓周期。
- 分批平仓是否在 `position_history` 产生多条明细，但在 `position_history_final` 只产生一条聚合记录。
- MFE/MAE 是否由 `PENDING` 变为 `CALCULATED`。
- Binance WebSocket 是否稳定连接。
- 合约 REST 接口是否正常，不再出现现货 ping 超时。
- 日统计和手续费是否与升级前基线一致。
- CPU、内存、数据库连接和日志增长是否正常。

生产环境首次真实交易验证应使用经过授权的最小风险订单；未经交易负责人确认，不要为了验收主动创建真实订单。

## 17. 回滚方案

### 17.1 尚未恢复生产流量

如果后台尚未恢复，或者升级后没有产生任何新订单：

1. 停止后台。
2. 切换回上一个稳定 Git 标签。
3. 恢复升级前数据库快照或 SQL 备份。
4. 恢复旧 Electron 客户端。
5. 启动旧版本并重新执行健康检查。

### 17.2 已经产生新订单或成交

如果升级后已经产生新订单、成交或持仓变化，不要直接恢复旧数据库，否则会丢失交易记录。

此时应：

1. 停止新的交易入口，但保留当前数据库。
2. 导出升级后新增的 orders、positions 和 position_history 数据。
3. 优先发布向前修复版本。
4. 如果必须回滚，由数据库负责人制定数据合并方案后再操作。
